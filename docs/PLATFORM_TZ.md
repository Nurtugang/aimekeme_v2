# Платформа видеонаблюдения — ТЗ для разработки (MVP)

## 1. Архитектура и Контекст

Система состоит из трех частей:

1. **AI-API (готовый репозиторий, зафиксирован):** Stateless-сервис на GPU. Принимает кадры/клипы, возвращает сырой инференс.
2. **Платформа / Backend + Broker (разрабатываемый сервис):** Подключает RTSP-потоки, опрашивает AI-API, сглаживает ошибки инференса, создает подтвержденные события, ведет историю занятости и раздает данные на фронтенд.
3. **Frontend (разрабатываемый интерфейс):** Осведомительный UI оператора (дашборд, живой видеопоток, события, лица).

```
[Камера RTSP] ──> [Broker (Python)] ──POST /detect/<module>──> [AI-API]
                        │  декод ОДИН раз на камеру
                        │  + медиана / N-из-M / дедуп / cooldown
                        │  (сырой инференс -> подтвержденное СОБЫТИЕ)
                        ▼
            [Backend (FastAPI) + SQLite + WebSocket]
                        │
                        ▼
            [Frontend (React): дашборд, лента, лица]

```

### Контракт AI-API (Не меняется!)

* `POST /detect/fight` — `{ "frames": [16 × base64_jpg] }` → `{ label, confidence, processing_ms }`
* `POST /detect/face` — `{ "frame": base64_jpg }` → `{ faces:[{box, det_confidence, identity, identity_id, similarity}], count, processing_ms }` (`identity` = имя или `"unknown"`; `identity_id` = ID человека или `null`).
* `POST /detect/fire` — `{ "frame": base64_jpg }` → `{ label, confidence, processing_ms }` (`fire` / `smoke` / `normal`).
* `POST /detect/counting` — `{ "frame": base64_jpg }` → `{ label:"person", count, confidence, processing_ms }`.
* `GET /health`

**Управление базой лиц (в AI-API):**

* `POST /faces` (multipart: `name` + `images` 1..N файлов) → `{ id, name, created_at, photos }`
* `POST /faces/{id}/images` → дозагрузка фото
* `GET /faces` → список всех лиц
* `GET /faces/{id}/image` → первичное фото (JPEG)
* `DELETE /faces/{id}` → удалить человека

## 2. Сущности БД (SQLite)

```sql
-- Пользователи
User { 
  id, username, password_hash, created_at 
}

-- Камеры и их конфигурация
Camera {
  id, 
  user_id (FK -> User), 
  name, rtsp_url, location, enabled,
  modules_config (JSON), -- Вкл/выкл и пороги (см. пример ниже)
  created_at
}

-- Настройки интерфейса
UserSettings {
  user_id (FK -> User, unique),
  layout_mode ("grid" | "focus"),
  active_camera_ids (JSON),     -- Список ID камер в текущем мониторинге
  focused_camera_id (FK -> Camera, nullable)
}

-- Подтвержденные события (эпизоды, НЕ сырые вызовы)
Event {
  id, camera_id (FK -> Camera),
  module,        -- fight | fire | face | counting
  label,         -- "fight" | "fire" | "smoke" | "Имя Человека" | "count > 30: 34"
  subject,       -- Ключ дедупа: identity_id | метка ("fire"/"smoke") | id-условия | null
  severity,      -- "alarm" (fight/fire) | "info" (face/counting)
  confidence,
  started_at, ended_at, -- ended_at = null пока статус OPEN
  seen (bool),   -- Прочитано оператором
  clip_path?     -- Опционально: путь к клипу ~10с (для fight/fire)
}

-- История занятости (метрика counting)
Occupancy {
  id, camera_id (FK -> Camera),
  count,         -- Медианное число людей за интервал
  ts             -- Снимок раз в ~1 мин
}

```

### Структура `Camera.modules_config` (JSON)

```json
{
  "fight": { "on": true },
  "fire": { "on": true },
  "face": { "on": false },
  "counting": {
    "on": true,
    "conditions": [
      { "id": "cond_1", "op": ">", "value": 30 },
      { "id": "cond_2", "op": "==", "value": 0 }
    ]
  }
}

```

## 3. Брокер и обработка результатов AI-API

> ⚠️ **Главное правило:** Ответ AI-API — это сырой инференс по одному кадру/клипу. Он stateless и может ошибаться. Брокер обязан агрегировать ответы перед записью события в БД и отправкой уведомления.

### 1) Захват потока и Back-pressure

* На каждую камеру вызывается `cv2.VideoCapture(rtsp_url)` — **ОДИН** декод на камеру.
* **Back-pressure:** Не отправлять новый запрос в AI-API по камере, пока не вернулся предыдущий. Очередь не копим — свежий кадр важнее, старые дропаем.

### 2) Сводная таблица работы модулей

| Модуль | Вход | Частота опроса | Алгоритм сглаживания (Буфер K) | Условие создания Event | Severity / Subject (дедуп) |
| --- | --- | --- | --- | --- | --- |
| **fight** | Клип 16 кадров | Шаг 8 кадров (~0.25–0.5 с) | Подтверждено, если **≥ 2 из 3** последних окон = fight | Включен модуль fight | alarm / subject = null |
| **fire** | 1 кадр | Раз в 1–2 с | **Медиана** последних K=5 ответов = fire/smoke (держится ≥ T сек) | Включен модуль fire | alarm / subject = "fire" или "smoke" |
| **face** | 1 кадр | Раз в 1–2 с | Узнан (identity_id ≠ null) в **≥ 2 из 3** последних кадров | Узнан человек из базы (identity_id ≠ null). *Неизвестные — только оверлей.* | info / subject = identity_id |
| **counting** | 1 кадр | Раз в 1–2 с | Рабочее число = **Медиана** последних K=10–15 замеров (~15–30 с) | Сработало условие из modules_config (напр. count > 30) | info / subject = condition_id |

*Примечание по counting:* Помимо условий, раз в **1 минуту** медианное значение `count` записывается в таблицу `Occupancy` (без создания `Event`).

### 3) Дедупликация и Машина состояний эпизодов

Чтобы не плодить сотни уведомлений, пока ситуация продолжается, брокер ведет машину состояний по ключу дедупа `(camera_id, module, subject)`:

1. **OPEN:** При выполнении условий подтверждения сменяется статус на OPEN → Создается **ОДНА** запись `Event` в БД + отправляется 1 WebSocket-уведомление.
2. **HOLD:** Пока сигнал держится — это тот же эпизод, события **НЕ дублируются**.
3. **CLOSE:** После M подряд "чистых" ответов (или ~T секунд без сигнала) эпизод закрывается (`ended_at = now()`).
4. **Cooldown (например, 60 с):** Повторный OPEN по этому же ключу в пределах cooldown приглушается.

## 4. Backend & API Платформы

* **Язык/Фреймворк:** Python (FastAPI).
* **Живое видео (RTSP):** Интеграция с **go2rtc** или **MediaMTX** (конвертируют RTSP → WebRTC/HLS для отображения в браузере).
* **Проверка RTSP при добавлении:** Кнопка "Проверить подключение" пробует открыть `cv2.VideoCapture` за 5 сек, берет 1 кадр и отдаёт картинкой на фронт. При ошибке сохранение формы не блокируется.
* **WebSocket:** Передает оверлей сырого инференса на видеопоток "здесь и сейчас", а также транслирует подтвержденные события для всплывающих уведомлений на дашборде.

## 5. UI/UX Гайдлайны и Экраны (Frontend)

### Гайдлайны стиля

* **Навигация:** Фиксированный левый сайдбар (Главная → Камеры → Управление камерами → Уведомления [с бейджем] → Лица → Лэйаут).
* **Плотность:** Тесная, плотная верстка (инструмент оператора).
* **Тема:** Светлая (белый/светло-серый фон, темный текст).
* **Акцентный цвет:** Циан/Тил (`#2BA9A0`) для активных элементов, кнопок, рамок выбранных камер. Без градиентов.
* **Тексты:** Нейтральные технические (без маркетинга).

### Экраны приложения

#### 1. Главная страница

Обзорная страница входа в систему.

#### 2. Дашборд (Мониторинг)

* **Пустое состояние:** Если нет активных камер — центр экрана со содержит кнопку "Добавить камеру".
* **Модалка выбора:** Позволяет выбрать, какие из добавленных камер мониторить прямо сейчас.
* **Сетка (Grid Mode):** 1 камера — 100% экрана; 2 камеры — 50/50; 3 камеры — 1 крупная + 2 мелкие; 4 камеры — 2×2; 5+ — авто-сетка NVR.
* **Фокус-режим (Focus Mode):** 1 крупная камера в центре, остальные миниатюрами снизу/сбоку (переключатель в сайдбаре "Лэйаут").
* **Оверлей на видео:** Результаты сырого инференса выводятся прямо поверх видео (боксы лиц, плашка "FIGHT", счетчик людей).

#### 3. Настройка модулей на камере (Меню "Три точки")

Вызывается прямо на окне камеры на дашборде:

* `fight`: Тумблер вкл/выкл.
* `fire`: Тумблер вкл/выкл.
* `face`: Тумблер вкл/выкл (уведомления только на людей из базы).
* `counting`: Тумблер + ввод порогов (`count >`, `count <`, `count ==`). *Если пороги пустые — пишутся только снимки занятости.*

#### 4. Лента событий / Уведомлений

* Постоянный журнал подтвержденных записей из таблицы `Event` (новые сверху).
* Поля строки: Время, Камера, Локация, Иконка/Северити, Текст ("Драка", "Иван", "Людей > 30: 34"), Ссылка на видеоклип (если есть).
* Клик по строке — пометить прочитанным (`seen = true`). Непрочитанные подсвечены и вызовут счетчик в сайдбаре.

#### 5. Страница «Лица»

* Список всех карточек из `GET /faces` AI-API (превью фото, имя, ID, число загруженных фото).
* **Форма создания:** Имя + загрузка 1..N фото.
* **Дозагрузка:** Кнопка "Добавить фото" на существующей карточке (`POST /faces/{id}/images`).
* **Удаление:** Кнопка-корзина (`DELETE /faces/{id}`).

## 6. Исключения для MVP (Чего НЕ делаем)

* Redis / внешние очереди сообщений (все очереди in-process в Python).
* Postgres / Мультитенантность / Аутентификация по ролям.
* Постоянная запись видеоархива (только клипы ~10с по тревоге).
* Пуш-уведомления в Telegram/Mobile.
* Сложная аналитика и трекинг уникальных людей за период.

## 7. Порядок разработки (Roadmap)

1. **Backend:** CRUD Камер + БД SQLite + WebSocket заготовка.
2. **Frontend:** Базовый каркас UI (Сайдбар, список камер, модалки).
3. **Broker (Базовый цикл):** Декод RTSP/видеофайла → отправка кадра в `/detect/fight` → **Агрегация (2 из 3) + Дедуп + Эпизод** → Создание `Event` → Трансляция в WebSocket.
4. **UI Модулей:** Меню "3 точки" на камере + сохранение `modules_config` + оверлеи.
5. **UI Событий:** Страница "Уведомления" с фильтрацией и счетчиком непрочитанных.
6. **Остальные модули в Брокере:** Подключение `fire`, `counting` (с записью в `Occupancy`), `face`.
7. **Интеграция Видео:** Подключение `go2rtc`/`MediaMTX` для живого HLS/WebRTC видеопотока на фронтенде.
